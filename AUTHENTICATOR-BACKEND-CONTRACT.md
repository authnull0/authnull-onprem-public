# AuthNull Authenticator — backend contract (WP1–WP8 delivered)

Everything in the app developer's backend plan is implemented. This is the wire contract to
build against: every endpoint, every field, every failure mode.

Nothing here is deployed yet. See [Deployment](#deployment) for the migrations and env vars
that must land first.

---

**Interop vectors:** [AUTHENTICATOR-TEST-VECTORS.md](AUTHENTICATOR-TEST-VECTORS.md) has a fixed
test key and byte-reproducible canonical payloads for v1, all four v2 combinations, and a full
request signature — generated by the server's signing helpers and checked by the server's own
verifiers. Reproduce those bytes and you are compatible. ECDSA is randomised, so verify the
signatures rather than byte-comparing them.

## 0. What the app needs to know first

**Three things authenticate, and they are not interchangeable.**

| Surface | Authentication | Why |
|---|---|---|
| Enrollment (`confirmSetup`, `RegisterDevice`) | the **enrollment token** | The phone has no key yet. The token is the credential; it is single-use with a 7-day TTL. |
| Challenge respond | the **response signature** (`authnull-mfa-response-v2`) | Proves the answer came from the enrolled device, not from anyone who guessed a challenge id. |
| Device self-service (`/api/v1/device/*`) | the **request signature** (`authnull-device-request-v1`) | These endpoints repoint where a push goes and can unenroll. Left open, they would be a hijack primitive. |
| `selfEnroll` | a **browser session** | Mints invites, so it is console-only. |

**One binary, many deployments.** The v2 invite payload carries `baseUrl`. Use it. Do not
compile a host in, and do not assume the SaaS host — the on-prem installs are the majority of
this product's deployments and none of them are reachable at `*.authnull.com`.

**The countdown comes from the server.** `getChallenge` returns `ttlSeconds` and
`secondsRemaining`. A hardcoded timer drifts from the server *and* from the AD gateway's own
timeout, and the user then approves something already abandoned. The current TTL is **60s**,
matching the DC sensor's `mfa_timeout_seconds`.

## 1. Invites (WP4)

### The v2 payload

```
authnull://enroll?v=2&d=<unpadded base64url JSON>
```

```json
{
  "v":  2,
  "b":  "https://onprem.dev.authnull.com",   // baseUrl — the API root to redeem against
  "o":  2,                                    // orgId
  "t":  16,                                   // tenantId (domainId)
  "n":  "Acme Corp",                          // orgName, for the confirm screen
  "h":  "acme.authnull.com",                  // orgHost
  "e":  "satyam@authnull.com",                // email
  "k":  "ad",                                 // "ad" | "platform" — which confirm endpoint
  "tk": "<enrollment token>",
  "x":  1770000000                            // expiry, unix seconds
}
```

Keys are single letters and the encoding is unpadded, to keep the QR's version low — a denser
code is measurably harder to scan off a laptop screen at arm's length. `k` tells you which
confirm endpoint redeems it; that is the only branch you need.

### Three link shapes must parse

Register all three schemes. Invites minted before v2 are already in inboxes and there is no
flag day.

| Shape | Kind | Carries a base URL? |
|---|---|---|
| `authnull://enroll?v=2&d=…` | from `k` | **yes** |
| `authnull://ad-enroll?token=…&orgId=…` | `ad` | no |
| `authnull://mfa-push-enroll?token=…&tenantId=…&orgId=…&email=…` | `platform` | no |

For the two legacy shapes, fall back to whatever server the app is already configured for, or
call `getEnrollmentDetails` — it returns `baseUrl`.

Accept a **bare compact payload** too (no URL wrapper): some QR readers hand over just the
`d` value. Accept padded base64url as well; some clients re-encode.

### Reading an invite before redeeming it

`GET /ad/getEnrollmentDetails?token=<t>&orgId=<o>`

```json
{
  "message": "ok", "code": 200, "status": "Success",
  "reason": "ok",
  "email": "satyam@authnull.com",
  "orgId": 2, "tenantId": 16, "userId": 41,
  "orgName": "Acme Corp", "orgHost": "acme.authnull.com",
  "role": "Org Admin", "roleSource": "role",
  "baseUrl": "https://onprem.dev.authnull.com",
  "kind": "ad",
  "expiresAt": "2026-08-18T09:14:22Z"
}
```

**`reason` is the field to branch on**, and it is populated on the 404s too:

| `reason` | HTTP | What to show |
|---|---|---|
| `ok` | 200 | the confirm screen |
| `used` | 404 | "This invite was already used — check your other phone" |
| `expired` | 404 | "This invite expired — ask your administrator for a new one" |
| `unknown` | 404 | "This link isn't valid" |

`used` is reported ahead of `expired` when both apply: "you already used this" is the more
actionable message, and a used invite usually expires later anyway.

`roleSource` says what `role` actually is — `"role"` for platform users (a real role from
`did.user_roles_permission`) and `"job_title"` for AD users, who have no role in the product.
Label it honestly; do not print a job title under a heading that says Role.

### Self-enrollment from the console

`POST /api/v1/mfa/push/selfEnroll` — **session-authenticated, empty body.**

```json
{
  "payload": "<compact base64url>",
  "deepLink": "authnull://enroll?v=2&d=…",
  "qrPngBase64": "iVBORw0K…",
  "orgName": "Acme Corp", "orgHost": "acme.authnull.com",
  "email": "satyam@authnull.com",
  "role": "Org Admin", "roleSource": "role",
  "expiresAt": "2026-08-18T09:14:22Z"
}
```

There is deliberately **no `orgId`, `email` or `userId` field to send.** The identity comes
only from the session cookie. This is not an oversight to work around: `AuthnzMiddleware`
proves that *a* valid session exists, it does not check that the session belongs to the
account named in a body — so minting from body fields would let any authenticated user in any
tenant request an enrollment invite for any account in any other tenant, and that invite
grants a device the ability to approve that account's MFA.

### Org discovery (optional, off by default)

`GET` or `POST /api/v1/device/discover` — for the manual-entry path where the user has an
email address and no invite.

```
GET  /api/v1/device/discover?email=satyam@authnull.com
POST /api/v1/device/discover   {"email":"satyam@authnull.com"}
```

→ `{"baseUrl":…, "orgId":2, "tenantId":16, "orgName":…, "orgHost":…, "email":…}`

Prefer POST: an email in a query string lands in nginx access logs, upstream proxy logs and
the phone's URL history.

**Expect 404 in most deployments.** This is an account-enumeration oracle, so it is off unless
`ORG_DISCOVERY_ENABLED` is set, rate-limited to 10/min per IP when on, and *disabled* and
*unknown address* return byte-identical 404s — you cannot detect whether it is enabled. A 503
means the server declines to answer right now (no rate limiter available) and says nothing
about the address. **Treat discovery as a nicety and the QR as the real path.**

## 2. Enrollment redemption

Both are unauthenticated by design — the enrollment token is the credential.

**AD** (`kind: "ad"`): `POST /ad/RegisterDevice`
**Platform** (`kind: "platform"`): `POST /authentication/push/confirmSetup`

```json
{
  "orgId": 2, "tenantId": 16,
  "enrollmentToken": "<tk from the invite>",
  "pushTransport": "fcm",
  "pushToken": "<FCM registration token>",
  "platform": "android",
  "deviceName": "Pixel 8",
  "publicKey": "<base64 DER SPKI, ECDSA P-256>",
  "publicKeyAlg": "ecdsa-p256"
}
```

- `400 "invalid or expired enrollment token"` — the token was unknown, used or expired. Call
  `getEnrollmentDetails` for the `reason` if you want to say which.
- **One phone, one device row.** If this phone already enrolled for the other flow, the
  registry reuses the existing row and adds the identity link. One device, one push token, one
  unenroll.
- The `publicKey` you send here is the **signing key**. Generate it hardware-backed and
  non-exportable. A separate biometric key comes later (§5).

## 3. Receiving and answering a challenge

### The push (FCM HTTP v1)

Sent as **notification + data**, never data-only: a `notification` block with title and body,
alongside `data`. iOS throttles silent data pushes and will not reliably wake a terminated app,
which for a 60-second challenge is a missed approval.

Android: `android.priority: HIGH`, `android.notification.channel_id: authnull_mfa`, plus a TTL
matching the challenge. iOS: `apns-priority: 10`, `apns-push-type: alert`,
`aps.interruption-level: time-sensitive`, `mutable-content`, and `aps.category` for actionable
buttons.

**The keys are `snake_case`, not camelCase.** Every value is a string — FCM rejects the whole
send if any is not.

| key | both flows | notes |
|---|---|---|
| `challenge_id` | yes | the id to pass to `getChallenge` / `respond` |
| `flow` | yes | `ad` \| `platform` — selects which respond endpoint |
| `org_id` | yes | **required** by `getChallenge`; a push without it cannot be resolved |
| `tenant_id` | yes | |
| `fetch_token` | yes | the credential for `getChallenge` |
| `expires_at` | yes | RFC3339 |
| `base_url` | yes | the deployment that issued this challenge |
| `type` | yes | `ad_mfa` \| `platform_mfa` |
| `user_email` / `binding_message` | AD only | |
| `email` | platform only | |

Both flows deliberately carry the same identifying set (`challenge_id`, `flow`, `org_id`,
`tenant_id`, `fetch_token`, `expires_at`, `base_url`), so one parser handles either.

**Route on `base_url`, not on `org_id`.** One app-store binary serves the SaaS and every on-prem
install, and one FCM token on the phone serves every enrollment on it — so `org_id` alone is
ambiguous the moment someone enrolls against two servers that both have an org 2. `base_url`
names the deployment that issued the challenge, so there is no guess to make.

**Never present a `fetch_token` to a server that did not issue it.** That token is the only thing
protecting the requester's email, source IP and target resource; broadcasting `getChallenge` to
candidate deployments to find the right one hands a live credential to servers with no business
seeing it. If you ever cannot identify the issuer, fall back to an "open the app to review"
prompt.

**Create the `authnull_mfa` notification channel at first run.** Without it Android silently
downgrades the notification and a 60-second challenge is missed.

### The context

`POST /authentication/push/getChallenge`

```json
{"orgId": 2, "flow": "ad", "challengeId": "1841", "fetchToken": "<fetch_token from the push>"}
```

```json
{
  "status": "pending",
  "expiresAt": "2026-08-11T09:15:22Z",
  "ttlSeconds": 60, "secondsRemaining": 47,
  "requester": "satyam@authnull.com",
  "resource":  {"name":"salesdb","type":"Database","id":"MSSQLSvc/db01.acme.local:1433","protocol":"kerberos"},
  "location":  {"ip":"10.2.14.7","city":"Pune","region":"MH","country":"India","display":"Pune, India"},
  "risk":      {"level":"HIGH","reasons":["new_country","impossible_travel"]},
  "bindingMessage": "Approve database login — salesdb from 10.2.14.7",
  "requireBiometric": true
}
```

**`requireBiometric` tells you whether to prompt.** It is resolved with the same lookup the
respond path enforces with, so you are never told one thing and held to another. Prompt for user
verification and sign with the biometric key when it is true; sign with the ordinary key when it
is false, rather than asking for a biometric the account did not require.

**`fetchToken` is mandatory.** Challenge ids are sequential integers, so an endpoint returning
requester email, source IP and target resource keyed on that id alone would let anyone walk
the ids and read who is logging in where. The token is 32 random bytes delivered only inside
the push, and only its SHA-256 is stored.

Any rejection is `401 {"error":"unauthorized"}` — one shape for all of them, so a caller
cannot confirm which challenge ids exist.

**A late tap returns 200 with the true status, not 404.** `expired`, `approved` and `denied`
are normal answers here; render "this request expired" rather than an error. The status comes
from the authoritative store (`did.ad_mfa_challenges` for AD, Redis for platform), never from
the activity mirror, so it will not show `pending` for something the gateway already gave up
on.

### The answer

Two endpoints, because the two flows key their challenges differently. `getChallenge` is
shared; respond is not.

**AD** — `POST /ad/RespondMFAChallenge`:

```json
{
  "orgId": 2,
  "adChallengeId": 1841,
  "approved": true,
  "signature": "<base64 ASN.1 DER ECDSA>",
  "signedAt": "2026-08-11T09:14:31Z",
  "signatureVersion": 2,
  "userVerified": true
}
```

**Platform** — `POST /authentication/push/respond`:

```json
{
  "challengeId": "8f3c…",
  "approved": true,
  "signature": "<base64 ASN.1 DER ECDSA>",
  "signedAt": "2026-08-11T09:14:31Z",
  "signatureVersion": 2,
  "userVerified": true
}
```

The signature fields are **flat, not a nested object**, and identical across both. The
platform challenge id is a UUID and carries its own org, which is why that request has no
`orgId`.

Signed bytes, **pipe-joined**:

```
v1:  authnull-mfa-response-v1|<challengeId>|approve|<signedAt RFC3339 UTC>
v2:  authnull-mfa-response-v2|<challengeId>|approve|<signedAt RFC3339 UTC>|uv=1|<keyId>
```

`approve` or `deny`. For AD, `<challengeId>` is the decimal `adChallengeId`. `keyId` is the
lowercase hex SHA-256 of the DER SPKI of **the key you signed with** — so a response signed by
the ordinary key cannot be presented as one signed by the biometric key. `uv=1` only when you
signed with the biometric key.

**Send `signatureVersion: 2`.** v1 still verifies, but only v2 can satisfy an account with
`requireBiometric` on — a v1 payload has no uv field at all, so a v1 client is rejected
outright for those accounts with `401 "response signature rejected"`.

**There is no v2 → v1 fallback, deliberately.** With one, a v1 signer could set
`userVerified: true` as plaintext beside a valid v1 signature and the server would believe it,
because the v1 payload does not cover that field. The declared version says which bytes were
signed; changing `userVerified` after signing invalidates a v2 signature.

`signedAt` is `time.RFC3339` in **UTC** — `2026-08-12T09:14:31Z` — and must be within
**5 minutes** of server time. It must be the same string you signed, byte for byte.

**Retrying is safe.** Respond is idempotent per `(challengeId, approved)`: repeating the **same**
decision returns `200` with `status` and `message` naming the recorded outcome, so a lost reply
can simply be retried. A **contradicting** decision returns `409` — the first answer is the one
already acted on, and a device cannot flip a verdict after the fact. A challenge that expired
before you answered returns `400 "challenge expired"`.

### require-biometric, concretely

When any account on this device has `requireBiometric` set, the server verifies the signature
against the device's **biometric key** — the second keypair whose keystore ACL demands user
verification. So:

- Register a biometric key at `/api/v1/device/key/biometric` before offering the toggle.
- Sign with that key, and set `userVerified: true`, whenever any account in the challenge
  requires it.
- Signing with the ordinary key while claiming `userVerified: true` fails, because the key id
  is inside the signed bytes.

**Biometrics gate approval, not refusal.** A **denial** is always accepted from the ordinary key,
with `userVerified: false`, even on an account with `requireBiometric` set — including from a v1
client. Refusing access is fail-safe (a forged denial only denies the forger, and still needs the
device's private key), whereas holding denials to the strict bar would leave a user whose
biometric key has been invalidated — new fingerprint enrolled, passcode changed, device restored
— unable to refuse anything while an attacker keeps retrying. A denial still has to be **signed**
by the device; only the *choice of key* is relaxed.

The self-reported `userVerified` flag on its own is an audit signal only — a repackaged app can
set it without ever prompting. The assurance is which key produced the signature.

## 4. Push token refresh — do not skip this

`POST /api/v1/device/pushToken/refresh` (signed)

```json
{"pushTransport": "fcm", "pushToken": "<new token>"}
```

Call it from `onTokenRefresh`, **every time**. This is the endpoint that stops "push MFA
silently stopped working" — an FCM token rotates on reinstall, restore and occasionally on its
own, and until this lands the server keeps pushing to a dead token and the user sees nothing
at all.

`409` means the token is already claimed by another device row: re-enroll.

The server independently retires dead tokens, but only on an unambiguous signal —
`UNREGISTERED`, HTTP 404, or an `INVALID_ARGUMENT` naming `message.token`. Transient FCM
errors never deactivate a device.

## 5. Device self-service (`/api/v1/device/*`)

Every route is **POST with a JSON body, including the reads.** A body-less GET would give an
attacker a signature valid for that route with no further constraint; a body — even `{}` —
binds each call to its own content.

| Route | Body |
|---|---|
| `/accounts/list` | `{}` |
| `/activity` | `{"before":"<RFC3339 cursor>","limit":50,"statuses":["denied"]}` |
| `/accounts/update` | `{"id":7,"pushEnabled":true,"requireBiometric":false,"displayName":"Work"}` |
| `/accounts/remove` | `{"id":7}` |
| `/pushToken/refresh` | `{"pushTransport":"fcm","pushToken":"…"}` |
| `/rename` | `{"deviceName":"Pixel 8"}` |
| `/push` | `{"enabled":false}` |
| `/unenroll` | `{}` |
| `/key/biometric` | `{"publicKey":"<base64 DER SPKI>","publicKeyAlg":"ecdsa-p256"}` |

`/accounts/list` returns the device and its accounts:

```json
{
  "device": {"deviceName":"Pixel 8","platform":"android","pushTransport":"fcm",
             "pushEnabled":true,"hasBiometricKey":true,
             "enrolledAt":"…","lastUsedAt":"…"},
  "accounts": [{"id":7,"orgId":2,"email":"satyam@authnull.com","identityKind":"ad_user",
                "displayName":"Work","pushEnabled":true,"requireBiometric":false}]
}
```

**Scoped to the org in the signature header.** Device rows live in the per-org database, so this
returns that org's accounts only — **one list call per (deployment, org)**. A phone enrolled
against several orgs on one deployment holds one row per org, all sharing the same key id, and
the `device` block repeats across them. `orgId` is therefore redundant per request but included
so a merged screen stays unambiguous.

`/activity` returns this phone's own MFA history, newest first:

```json
{
  "items": [{"flow":"ad","challengeId":"1841","email":"…","status":"denied",
             "resolutionSource":"device",
             "resource":{…},"location":{…},"risk":{…},
             "bindingMessage":"…","createdAt":"…","respondedAt":"…"}],
  "nextCursor": "2026-08-11T09:02:14Z"
}
```

Scoped to the signed device, never to a device id you send — the activity table holds the whole
organisation's challenges. `resource`, `location` and `risk` are the **same shapes**
`getChallenge` returns, so one model parses both. Page by passing the previous `nextCursor` as
`before`; an absent `nextCursor` means that was the last page. `limit` defaults to 50 and caps at
200. `resolutionSource` is `device` | `provider_poll` | `ttl` — the difference between "the user
denied it" and "nobody answered".

Only show the require-biometric toggle when `hasBiometricKey` is true. The server refuses to
enable it without a registered user-verification key — otherwise the user enables a
requirement no response can satisfy and locks the account out of push entirely.

`id` is the account row id, which you echo back. There is no way to name a device: it comes
from the signature, because a client-supplied device id would let one signed phone manage
another's.

### Request signatures (`authnull-device-request-v1`)

Headers:

```
X-Authnull-Device-Alg:        ecdsa-p256
X-Authnull-Device-Org:        2
X-Authnull-Device-Key:        <keyId>
X-Authnull-Device-Nonce:      <unique per request>
X-Authnull-Device-Timestamp:  <unix seconds>
X-Authnull-Device-Signature:  <base64 ECDSA>
```

Signed bytes, **newline-joined** (note: the response signature is pipe-joined; these two
formats are different and neither will verify as the other):

```
authnull-device-request-v1
POST
/api/v1/device/accounts/update
2
<keyId>
<nonce>
<unix timestamp>
<base64(sha256(raw body))>
```

- The route is the **gin route pattern**, i.e. exactly the path in the table above.
- `keyId` = lowercase hex SHA-256 of the DER SPKI public key.
- The nonce must be **16–128 characters** of `[A-Za-z0-9-_]` only — url-safe base64 or hex. A
  shorter one is rejected outright, which is easy to miss because the failure is the same
  blanket `401` as everything else. 32 hex characters or a base64url-encoded 16 random bytes are
  both fine.
- The nonce is single-use for 5 minutes. Reuse is rejected.
- Timestamp within 5 minutes of server time.
- Body limit 64KB.
- Every rejection is `401 {"error":"unauthorized"}`, without exception.

These endpoints are mounted at `/api/v1/device/*` and **nowhere else**, because you sign the
route pattern — the same handler reachable at two patterns would mean a signature valid at one
path is rejected at the other.

## 6. What the server does on its own

Nothing here needs an app change; it is listed so behaviour you observe is not mistaken for a
bug.

- **Risk scoring** (`MFA_PUSH_RISK_ENABLED`) — first activity, new source IP, new country,
  impossible travel (>900 km/h), off-hours against a learned baseline, a recent denial, push
  velocity (≥4 in 5 min). Surfaced as `risk` on `getChallenge`.
- **Geo** (`MFA_PUSH_GEO_MODE`) — private, loopback, link-local and CGNAT addresses
  short-circuit before any network call.
- **Fraud alerts** — a denial can trigger an email, once per 15 minutes per account, sent
  after the response so it never delays an authentication.
- **Sweeper** (`MFA_PUSH_SWEEP_ENABLED`) — a daily job expiring stale pending rows across every
  org database. Both flows only expire a challenge when something polls, so a crashed gateway
  otherwise leaves rows pending forever and the activity history lies.
- **Activity mirror** — `did.mfa_push_activity`, one row per challenge, for history and the
  risk lookback. Authoritative status stays where it was.

## 7. Deployment

### Migrations — not yet applied anywhere

`db-init/migrations/` is replayed against the master database and every org database on every
boot (`docker-compose.yml:144-165`), so deploying is enough to apply these. They are all
idempotent.

| | |
|---|---|
| `004_ad_enforcement_mode.sql` | dashboard-controlled sensor mode — **already deployed** |
| `005_mfa_device_selfservice.sql` | `key_id`, biometric key, per-account prefs |
| `006_mfa_push_activity.sql` | the activity mirror |

Note that `internal/*/db/migrations/` is inert — nothing replays those.

### Environment

**FCM is now configured.** Firebase project **`authnull-one`**, service account
`firebase-adminsdk-fbsvc@authnull-one.iam.gserviceaccount.com`. The credential is bind-mounted
read-only at `/run/secrets/fcm-service-account.json` from `./secrets/` on the host, which is
gitignored — a Firebase key cannot be scoped down (it grants send-to-any-device across the whole
project), so it must never enter git, and `.env` is committed in this repo. Verified with a real
OAuth token exchange through the same `newFCMSender` the push path uses.

Send endpoint: `https://fcm.googleapis.com/v1/projects/authnull-one/messages:send`.

**The app must be built against the `authnull-one` Firebase project**, or the registration tokens
it mints belong to a different project and every send returns `INVALID_ARGUMENT`. Note the APNs
key still has to be uploaded to that project or iOS pushes fail silently — see §8.

| Variable | Effect if unset |
|---|---|
| `FCM_SERVICE_ACCOUNT_JSON` | **no pushes are sent at all.** Path or inline JSON; this deployment uses the mounted path. |
| `API_BASE_URL` | falls back to `SYSTEM_URL`, then the client URL. Required on split deployments, or invites carry the wrong base URL. |
| `MFA_PUSH_CHALLENGE_TTL_SEC` | 60s. Values above 60 are warned about — the AD gateway gives up at 60 and a longer window means a user approves something already refused. |
| `ORG_DISCOVERY_ENABLED` | discovery 404s. Leave unset unless the manual-entry path is needed. |
| `MFA_PUSH_RISK_ENABLED` | no risk scoring; `risk.level` is empty. |
| `MFA_PUSH_GEO_MODE` | `off`. `mmdb` needs a reader compiled in — `geoip2-golang` is **not vendored**, so `mmdb` currently logs and returns nothing. |
| `MFA_PUSH_SWEEP_ENABLED` | stale pending rows are never reaped. |
| `MFA_PUSH_ALLOW_UNSIGNED` | signatures enforced. **Leave it unset.** Anything unparseable is treated as enforce, so a typo fails secure. |
| `APP_IOS_URL`, `APP_ANDROID_URL` | placeholder store links in the invite email. Set these before the app ships. |

### Verifying after deploy

1. `POST /authentication/push/confirmSetup` with a bogus `enrollmentToken` → **400**, not 401.
   A 401 means it is still landing on the authenticated group.
2. `POST /api/v1/mfa/push/selfEnroll` with no session → **401**. With a session → a QR whose
   payload's `o` is the session's org, whatever the body says.
3. `GET /api/v1/device/discover?email=…` → **404** unless `ORG_DISCOVERY_ENABLED` is set.
4. Any `/api/v1/device/*` call with no signature headers → **401 `{"error":"unauthorized"}`**.
5. Replay a `/api/v1/device/rename` call verbatim → the second is **401**.
6. Scan an invite QR → the payload contains `b` with this deployment's API base.

## 8. Still open

- **iOS**: the service account covers both platforms via FCM, but an **APNs auth key must be
  uploaded to the `authnull-one` Firebase project** or iOS pushes fail silently — FCM accepts the
  send and drops it. This is the most likely reason for "works on Android, nothing on iPhone".
- **Store URLs**: `APP_IOS_URL` / `APP_ANDROID_URL` are placeholders in the invite email.
